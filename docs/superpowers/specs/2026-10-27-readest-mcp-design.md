# Readest MCP: shared interface, cloud and local sources

Date: 27 October 2026. Planning baseline; product implementation has not started. This consolidates the subsequent conversation and supersedes the local-only draft in `outputs/2026-10-26-readest-mcp-design.md`. Numerical limits, dependency choices and operational defaults below are engineering proposals for review, not additional promises made by the user.

## Intent and choices

Build a small, standalone, read-only MCP for personal reading and research, shared publicly as `gbettineschi/readest-mcp`. Support EPUB and PDF, library browsing, saved reading state, highlights, comments, bookmarks, excerpts, notebook entries, available ink records, keyword and optional local semantic search, and retrievable source references. The assistant writes answers; this server supplies evidence rather than running an answer-generation model.

The user chose a fresh implementation using the official MCP SDK rather than extending the existing servers or maintaining a Readest app fork. For source acquisition we considered automatic local/cloud fallback, separate MCPs, and one MCP configured with one source. The current direction is one source selected at setup, one shared interface, and two internal adapters. This avoids silently mixing accounts, freshness, identities and coverage. Direct Google Drive access would be a third adapter and is outside this release: Drive users use the data saved by stock Readest.

## Architecture and public contract

The boundary is `MCP -> shared services/index -> LibrarySource -> local or cloud adapter`. Only the composition/configuration code selects the adapter. Tool handlers, extraction, indexing, search and reference resolution must not branch on source mode. Provider-specific details stay within the adapter and its credentials module.

- Same six tool names, short descriptions, input schemas, output schemas and annotations in both modes.
- Each tool has its own typed data payload. That payload has the same shape in both modes; book lists and search results need not have identical payloads to each other.
- Shared application result: `data`, `status`, `warnings`, `error`, `meta`. All five keys are present. `status` is `ok | partial | error`; `data` is the tool's payload or `null`; `warnings` is an array of `{code,message}`; `error` is `null` or `{code,message,retryable}`.
- `meta` contains `source: local | cloud`, `refreshed_at: ISO string | null`, `from_cache: boolean`, and `coverage: {scope: configured_source, completeness: complete | partial | unknown, known_books: number | null, covered_books: number | null}`. Coverage refers to the requested operation and targets, not every book the person owns. Counts may be unknown. A normal paginated list is not a partial failure.
- `ok` means the operation succeeded. It does not certify an exhaustive personal library or exhaustive conceptual search. Do not add a warning merely because the selected mode is local. Report only known limitations, and preserve unknown completeness.
- Expected source/domain failures use this same result shape, including authentication/network failures and unavailable content. MCP `structuredContent` and a JSON text rendering carry the same result. Set MCP `isError` only for `status:error`. Explicitly validate application error results too: SDK error responses may skip output-schema validation. Invalid protocol messages, a terminated process or an SDK rejection before our handler are outside this application-result guarantee.
- Failed refresh with usable prior data: `partial`, cached data, `from_cache:true`, and a specific refresh-failed warning. Failed refresh without usable data: `error`, `data:null`; never an invented empty library.

Six tools, with restrained descriptions:

| Tool | Description | Input and payload responsibilities |
|---|---|---|
| `library_status` | Get library availability and indexing status. | No arguments. Counts by catalogue/annotations/text, capabilities and last refresh outcome. |
| `list_books` | List books known to the configured source. | Pagination and metadata filters; returns book summaries and next cursor. |
| `get_book` | Get available information about a book. | Book ID, optional paginated structure; metadata, state, availability and structure. |
| `list_annotations` | List saved annotations for a book. | Book ID, filters, pagination; typed annotations and original locators. |
| `search_library` | Search available book text and annotations. | Query, keyword/semantic/hybrid mode, targets, filters, pagination; evidence hits and actual search mode. |
| `read_content` | Read available book content. | One structured selector: passage ID, structure ID, or annotation ID with surrounding text; bounded evidence. |

Pagination defaults to 20, maximum 50. Query maximum 1,000 characters; excerpt maximum 320 characters; content defaults to 4,000 and is capped at 12,000 characters. Serialized application results are capped at 64 KiB using pagination or an explicit truncation warning. Tool arguments accept IDs, not arbitrary paths, URLs, SQL or raw FTS expressions. Do not add separate commands meaning approximately "all books" and "available books".

Keep parameter names fixed too. Paged lists use `limit` and `cursor`. `list_books` takes optional `filters` (metadata query, author, tags, formats and saved reading status). `get_book` takes `book_id` and `include_structure` (default false). `list_annotations` takes `book_id`, optional types/colors/date bounds and pagination. `search_library` takes `query`, `mode` (default `keyword`), `targets` (default `book_text`, `quotes`, `notes`), optional book filters and pagination. `read_content` takes `selector: {kind: passage|structure|annotation, id}`, optional `cursor`, `max_chars` (default 4,000) and `context_chars` (default 0, within the overall content bound); its payload returns `next_cursor` for bounded continuation through long content. IDs returned by tools are opaque, source-scoped and sufficient to make the next call; callers do not construct filesystem locators. Paged list payloads use `items` and `next_cursor`; search also returns `requested_mode` and `used_mode`. Content cursors are bound to selector and revision so a long chapter can be read completely without an unbounded response.

## Source behavior

Local mode reads an explicitly selected or unambiguously detected Readest library and related saved configuration. Use a bounded platform-path list and overrides; never scan the whole home folder. Read `library.json`, available per-book `config.json`, managed files and authorized in-place files. Resolve real paths and reject escapes outside the configured library/additional content roots. Readest owns Drive/provider authentication and sync. Missing configuration means unavailable annotations, not zero annotations. Preserve unknown/missing fields and versioned migrations without copying the app's implementation. Do not import integration credentials or raw global settings.

Extraction and hashing operate on the same validated file snapshot. If a local book changes while that snapshot is acquired, retry once then report unavailability. File existence, preallocated size or momentary stability alone is not proof of a completed Readest download; container/page validation and extraction gaps remain explicit.

Cloud mode uses Readest's published sync implementation and documented account sign-in, not a fictional generic developer API. Establish a separate user session through the supported email/password flow used by its KOReader integration; a social-only account may need the user to set a password in Readest. Password entry is private and passwords are not stored. Keep only the renewable session in a private credential file outside the repository, directory mode `0700`, file mode `0600` on POSIX. No automatic extraction or sharing of the app/browser refresh token. Reconfirm the official public project configuration at implementation time; never use a service-role/admin key. Session renewal is serialized and saved atomically.

Pull books, configs and notes separately with independently committed checkpoints. Follow the exact pinned API's pagination and deletion semantics, including tied book cursors; do not invent a common timestamp cursor. Bulk download requests are read operations only when they request signed URLs. A code-level endpoint/method allowlist excludes pushes, uploads, source edits and deletes; auth endpoints are separately scoped. Download uploaded book files to the MCP's cache through validated signed URLs. Never forward account authorization to an arbitrary storage host or expose tokens/signed URLs in results or logs. Verify current hosted access/plan eligibility instead of assuming the account can use every channel.

Neither route guarantees another device's unsaved state. List known records separately from file presence, textual extraction/index availability and annotation availability. A known metadata record is not a downloaded book. Cloud has no direct access to Drive-only bytes. Local acquisition is passive: missing files require a download in Readest. No automatic app launch, download watcher, source switching, Readest fork or direct Drive OAuth in this release.

## Shared content, index and references

Use TypeScript, Node.js 24.15+ in the 24 LTS line, official stable SDK v2 (`@modelcontextprotocol/server`, client package for tests), Zod 4, SQLite FTS5 through `node:sqlite`, Mozilla PDF.js, and bounded ZIP/XML/HTML libraries. Proposed extraction libraries are `yauzl`, `fast-xml-parser` and `linkedom`; verify Node compatibility and licenses before pinning exact versions in the lockfile. No Python service, hosted backend or vector database.

EPUB 2/3 extraction follows container/package/spine and NAV/NCX, preserving recursive structure, chapter order, Unicode, paragraphs and deterministic offsets. Do not execute content or fetch its resources. PDF extraction preserves physical one-based pages and separate printed labels; report scan-only, mixed empty/text pages, passwords, corruption and layout limitations. Reject source files over 256 MiB, EPUB expanded content over 512 MiB or 20,000 entries, and extraction taking over 60 seconds. Limits are internal constants first, not a large configuration UI.

Normalize annotations as `bookmark | annotation | excerpt | notebook | ink`, keeping quoted text separate from the user's comment; retain IDs, timestamps, color/style and supplied CFI/page/xpointers. Preserve available ink strokes internally; omit bulky strokes from list results and allow bounded annotation payload retrieval through `read_content`. No handwriting recognition, OCR, image/formula understanding or complete editing history. A reading percentage/status is saved state, not proof of comprehension. Full settings mirroring, smart-shelf execution, listening analytics and a separate reading-activity tool are deferred, not implied by the basic reading-state fields.

Every evidence record includes book ID, byte-derived revision, passage ID, title/author, source kind and a structured location. EPUB offsets are not advertised as canonical CFIs. PDF physical pages and printed labels remain distinct. Preserve original annotation locators; contextual matching can be unresolved or ambiguous. Changed editions invalidate old references rather than resolving them to unrelated text. Cached evidence identifies its last indexed revision; an absent source file does not prove it is still the latest edition.

Store generated metadata, passages, FTS rows, fingerprints and embeddings in an external, source/account-partitioned cache. Cache/index writes are allowed; source writes are not. Refresh uses a single writer, transactional checkpoints and interruption-safe per-book updates. Explicit tombstones remove corresponding current evidence. Never treat an unreadable catalogue as an empty one, or failed annotation hydration as a deletion. A file being offloaded is different from a book being deleted; retained generated evidence must identify its revision/freshness. A corrupt book must not block healthy books.

Startup does not download/index an entire library. Shared CLI maintenance command `refresh --content available|all` defaults to `available`; `all` explicitly requests cloud acquisition where possible and reports missing local files. `refresh --rebuild` rebuilds generated data only. Reading one missing cloud passage can acquire that book on demand. Source metadata is refreshed at startup and after a five-minute cache age, once per in-flight refresh; failures follow the result rules above. Search never pretends to search text not yet indexed.

Keyword search uses parameterized FTS5/BM25 over separate book-text, quote and user-note targets, with Italian/English and diacritic tests. Semantic search is included as an optional local capability of the same `search_library` tool. Proposed provider: Transformers.js stable npm release with quantized `Xenova/multilingual-e5-small`, pinned model revision, E5 prefixes and normalized embeddings. Download the model explicitly through setup/`models fetch`; never upload book text for embeddings. Use bounded cosine scans of SQLite-stored vectors initially and measure representative-library cost. No ANN infrastructure or quality claims before evaluation. If unavailable, explicit semantic requests fail clearly; hybrid may fall back to keyword with `partial`, a warning and `used_mode:keyword`.

## Delivery, verification and documentation

Use synthetic public-domain/generated fixtures, never the user's books, credentials or cache. Test schema parity across both adapters, real SDK initialization and tool calls, source failure/cache cases, exact references, content gaps, deletion, interrupted refresh, path boundaries and local model retrieval. Distinguish fixture, clean-install, client-discovery and live-account evidence. Installed Readest 0.12.16 and its URL scheme were observed previously; no real cloud login, Drive download or personal-library search has been demonstrated. Recheck installation/storage at execution time.

Publish the requested public repository only after content, dependency-license and secret checks. MIT for original code, without copying Readest application code. Keep README short: purpose, configuration, examples, actual tested support and limitations. Maintenance note: "Built for my own reading and research, and shared in the hope that others find it useful. Provided as is; development follows my personal needs and available time. Thoughtful bug reports, fixes and contributions are welcome." Do not promise exhaustive search, universal compatibility or support response times. Initial distribution is build-from-source; npm publication/packaged installers are separate work.

Configure Codex only after fixture/clean-install verification, preserving all existing MCP entries. Check actual discovery separately from writing configuration. If local books or cloud sign-in are unavailable, finish independent work and state the precise unverified step; never call a fixture pass an account pass.
